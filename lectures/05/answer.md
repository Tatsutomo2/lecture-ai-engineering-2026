- 取り組んだレベル：実装
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  `app/retrieval.py` の `search` 関数を変更した。ベクトル検索の各結果（最大RAG_TOP_K件）に対し、同じ資料の前後1ページ分（-1, +1）の本文を追加取得し、`content`に結合して返すようにした。別の資料をまたいだり、取得済みのページが重複したりしないよう判定処理も追加した。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：`第3回の例では、コンパクションとセッションをまたぐメモリはどう違いますか。日々のメモはすべて長期メモリに入りますか？`
  - 固定条件：対象資料（第1〜3回の本講義）、モデル（gemini-3.5-flash-lite）、検索件数（RAG_TOP_K=5）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - 回答・根拠：変更前は第3回 p.39, 40, 65を引用して正答。変更後はそれに加えて「p.13」も引用され、セッションをまたぐメモリの説明が補強された。
  - `--trace`：変更前後とも `search_materials({'query': 'コンパクション セッション メモリ 長期メモリ 日々のメモ'})` を1回呼び出し。
  - 時間：5.13秒 → 4.82秒
  - 入力／出力トークン数：2,502 / 298 → 3,678 / 357（入力が約1.5倍に増加）
  - 生成API推定費用：$0.001496 → $0.001996（約33%増加）
- 改善した例と、残る失敗・制約：
  前後ページを追加したことで、変更前は引用されなかったp.13（セッションをまたぐメモリの具体例）が根拠に加わり、回答がより網羅的になった。
  一方で、ヒットした全ページの前後を機械的に結合するため、入力トークンとコストが増加する。話題が切り替わるページがヒットした場合は、無関係な情報がノイズとして混ざる制約がある。
- 気づき・疑問：
  説明が複数ページに分かれる質問に対し、前後ページの追加は有効だった。しかし、単に前後を足すだけでは情報量とコストが常に増えてしまう。Graphのように関連用語などを手がかりにする方式とは性質が異なるとわかった。コストを抑えつつ必要な情報だけを集めるには、さらなる工夫が必要だと感じた。
